# Deployment requirements: `99 Bottles`

Этот документ описывает только требования приложения и проверяемый результат. Он не задаёт конкретный сервер, абсолютные production-пути, пользователей ОС, права файлов, HTTP-конфигурацию или способ передачи релиза.

Не добавлять сюда значения секретов, приватные ключи, сертификаты, базы данных или резервные копии.

## Приложение

| Параметр | Значение |
| --- | --- |
| Название | `99 Bottles` |
| Репозиторий | `https://github.com/boxfrommars/bankirtest.dgroza.ru.git` |
| Production-ветка | `master` |
| Канонический URL | `https://bankirtest.dgroza.ru/` |
| Тип процесса | HTTP request |
| Runtime | PHP 8.3 |
| База данных | SQLite |

## Runtime-интерфейс

- Package manager: Composer.
- Установка production-зависимостей:

  ```shell
  composer install --no-interaction --no-dev --prefer-dist --optimize-autoloader --no-progress
  ```

- Относительный публичный каталог: `public/`.
- Entry point: `public/index.php`.
- Frontend-сборка: отсутствует; CSS, JavaScript и изображения хранятся в `public/`.
- Требуемые системные возможности: PHP 8.3, PDO SQLite, DOM, Fileinfo, Mbstring, OpenSSL, Session и Tokenizer; Composer должен удовлетворять требованиям `composer.lock`.
- Ограничения процесса: HTTP runtime должен иметь общий доступ к постоянной SQLite-базе, файловым sessions и cache; параллельная запись должна учитывать блокировки SQLite.

Все пути ниже задаются относительно корня приложения либо через имя переменной окружения. Способ запуска процесса и интеграцию с HTTP-сервером выбирает среда размещения.

## Состояние и запись

- Writable-пути runtime относительно корня: `storage/` и `bootstrap/cache/`.
- Генерируемые артефакты: `vendor/` после Composer install; runtime cache, compiled views, sessions и logs внутри `storage/` и `bootstrap/cache/`.
- Постоянные данные: SQLite-файл, заданный `DB_DATABASE`, и возможные SQLite sidecar-файлы в том же постоянном каталоге.
- Пользовательские загрузки: отсутствуют.
- Требование к согласованной backup-копии: перед миграцией, первоначальным seed или другой release-операцией, способной изменить schema или данные, обязательна свежая согласованная SQLite-копия. Обычное копирование работающего файла не считается согласованным backup.
- Проверка целостности и восстановления: backup должен пройти `PRAGMA integrity_check`; восстановление предварительно проверяется в отдельный временный файл.

Кеши, sessions, logs, `vendor/` и локальный Docker marker `.seeded` не являются заменой постоянной SQLite-базы. Marker относится только к локальному Compose lifecycle и не участвует в production initialization.

## Lifecycle hooks

### Установка production-зависимостей

- Момент выполнения: после доставки кода, до активации релиза.
- Команда:

  ```shell
  composer install --no-interaction --no-dev --prefer-dist --optimize-autoloader --no-progress
  ```

- Эффект: устанавливает зафиксированные в `composer.lock` production-зависимости.
- Изменяемые пути: `vendor/`.
- Изменение постоянных данных: отсутствует.
- Повторный запуск безопасен: да.
- Ошибка блокирует релиз: да.

### Очистка runtime-кешей

- Момент выполнения: после установки зависимостей, до сборки новых кешей.
- Команда:

  ```shell
  php artisan optimize:clear
  ```

- Эффект: удаляет устаревшие Laravel-кеши.
- Изменяемые пути: `bootstrap/cache/`, `storage/framework/`.
- Изменение постоянных данных: отсутствует.
- Повторный запуск безопасен: да.
- Ошибка блокирует релиз: да.

### Сборка runtime-кешей

- Момент выполнения: после очистки кешей, перед финальной проверкой релиза.
- Команда:

  ```shell
  php artisan optimize
  ```

- Эффект: создаёт актуальные Laravel production-кеши.
- Изменяемые пути: `bootstrap/cache/`, `storage/framework/`.
- Изменение постоянных данных: отсутствует.
- Повторный запуск безопасен: да.
- Ошибка блокирует релиз: да.

Миграции и seed не входят в обычные lifecycle hooks.

## Изменения данных

- Миграции: `php artisan migrate --force` как отдельный явно согласованный шаг релиза.
- Предусловия: свежий согласованный backup, проверенный target commit и отдельное решение о необходимости maintenance mode. Для несовместимого изменения запись должна быть остановлена на время миграции.
- Обратимость: определяется каждой миграцией. Автоматический `php artisan migrate:rollback` запрещён; `down()` начальной миграции удаляет все три таблицы и данные.
- Ожидаемая недоступность: отсутствует для доказанно совместимых миграций; иначе равна времени maintenance window и проверки данных.
- Совместимость старой и новой версии с данными: должна быть подтверждена в release-плане до запуска миграции.

Первоначальное заполнение новой пустой базы выполняется отдельно:

```shell
php artisan migrate --force
php artisan db:seed --force
```

`DatabaseSeeder` вставляет фиксированные ID и не является идемпотентным. Его нельзя запускать при обычном обновлении или в заполненной production-базе. `migrate --seed` не является штатной production-командой.

- Канонический URL: `https://bankirtest.dgroza.ru/`.

## Совместимость rollback

- Можно ли вернуть предыдущую версию кода без возврата данных: только если её совместимость с текущей schema и данными подтверждена заранее.
- Application-команды после возврата кода:

  ```shell
  php artisan optimize:clear
  php artisan optimize
  ```

- Требуется восстановление данных: если новая версия выполнила несовместимую миграцию или изменение данных, восстановить согласованную копию, соответствующую возвращаемому коду.
- Несовместимые изменения: удаление или переименование таблиц/полей, изменение смысла данных и повторный seed.
- Проверки после возврата: `/up`, главная, три коллекции, поиск, `/login`, 404 и целостность SQLite.

Выбор версии и операции среды размещения в этот документ не входят.
